iLumens: building and rescuing a device to cloud platform

An IoT telemetry platform that runs from sensor firmware in the ceiling to dashboards in the browser. I joined as a software engineer, left as technical lead, and along the way migrated its cloud platform, killed a database connection leak, and rebuilt its production Kubernetes environment after a failure.

The platform

Sensors and controllers in commercial buildings report occupancy, environmental, and device data. That data has to travel from constrained embedded hardware, over BLE and gateway hardware, into cloud services, and out to the Smart Room dashboards that facility teams actually use. Every layer in that chain was part of my job at some point.

My role

I started in December 2022 as a software engineer writing backend services and debugging device firmware. The work kept widening: first the data path between devices and cloud, then production incidents on GCP, then design and review responsibility, and in May 2024 I became technical lead of the eight person team.

The through line is that I owned problems across firmware, backend, cloud, and frontend rather than one layer. When a sensor reading was wrong on a dashboard, the fault could sit in a BLE state machine, a gateway packet, a sync job, a serializer, or a React widget, and my job was to follow it across those boundaries until the whole path worked. The five stories below are the ones that best show that.

Deep dives

Deep dive 1 · Platform migration

Migration without breaking the fleet

The platform ran on Astarte, and we moved production to ThingsBoard. The constraint that shaped everything: the installed device fleet and its BLE layer were stable and working, and a migration that broke them would have been a field problem, not a software problem.

  • Phased strategy. We evaluated several approaches and chose the one that preserved the stable BLE device layer while replacing only the ESP32 to cloud gateway path, which kept the blast radius small.
  • Sync rewrite. I rewrote device synchronization around the ThingsBoard device model, removing Astarte specific interface and endpoint abstractions, with device discovery, connectivity refresh, and stale device cleanup.
  • Normalization layer. I built telemetry normalization between ThingsBoard payloads and the application models, so frontend components were decoupled from platform specific response formats instead of breaking with each payload change.
  • User data protection. Automated sync had been able to overwrite user managed aliases and metadata. I replaced broad upserts with conditional update logic so synchronization updates device state without clobbering what operators had named and configured.
  • Ingestion resilience. I added retries with exponential backoff (1s, 2s, 4s, 8s, 16s, up to 5 attempts) and structured failure logging for transient telemetry ingestion errors, and verified with simulated intermittent network failures that payloads were recovered instead of dropped.

We also stress tested the migrated pipeline with malformed payloads, delayed responses, and interrupted transmissions, adding backend validation and frontend fallback states so partial or stale data did not reach users as if it were live.

Deep dive 2 · Backend debugging

The PostgreSQL connection leak

~99database connections open in production
~2of them actually active
0persistent idle connections after the fix

Production PostgreSQL was accumulating connections: about 99 open, with only about 2 active and the rest idle. The problem did not reproduce locally, which made it a production only investigation across cloud logs, PostgreSQL activity views, and the backend code.

The root cause sat in the data synchronization workers. The sync code made heavy use of Python threads doing Django ORM work, and when those threads finished, their database connection lifecycles were not released correctly, so idle connections accumulated until they became the problem.

The fix was an architecture change, not a settings tweak: I redesigned the synchronization concurrency around multiprocessing and a process pool, so connection ownership followed process boundaries that actually close. I validated the change in local, then test, then production. In production, the leak was gone.

Deep dive 3 · Platform recovery

Rebuilding production on GKE

In December 2024 the Astarte deployment began going offline at random. I worked through the cluster methodically: GKE CPU, memory, and storage, pod and node networking, DNS, ingress, liveness and readiness probes, autoscaling events, load balancer health checks, and GCP status. The infrastructure looked healthy while the platform kept degrading, until pods failed, operator and custom resource state fell out of sync, and the cluster went down.

The recovery turned out to be the real project. The backups were incomplete: there was no full usable snapshot to restore from. So in January 2025 I rebuilt the production environment by hand, across roughly 7 namespaces and 30 pods:

  • GKE cluster, namespaces, and workload deployments for the Django backend, Astarte, and Scylla.
  • Secrets reconstructed one by one, including the Astarte realm private key, database credentials, the Django secret, Keycloak settings, and GCP service account credentials, then rebound to service accounts.
  • Keycloak authentication rebuilt: realm, OAuth redirects, roles and groups, userinfo mappings, CORS and Web Origins, and session flows.
  • Ingress and TLS recovered by debugging cert manager HTTP-01 challenges, solver pods, DNS records, ClusterIssuers, and TLS secrets.
  • Node pools resized when the rebuilt workloads would not schedule within the existing CPU and memory.

One nested problem is worth naming on its own: the test backend could not reach its database because the GKE cluster and Cloud SQL sat in different VPCs. I evaluated VPC peering, found a subnet CIDR conflict, compared peering, Shared VPC, and a cluster rebuild, and chose the network restructuring that actually resolved it.

After the rebuild, I also migrated workloads to a smaller node pool, cordoning and draining the old nodes and retiring the pool, to bring the cluster cost back in line with what the workloads actually used.

Deep dive 4 · GOAT · Integration leadership

GOAT: integrating a real time training system

GOAT is a U.S. Department of Energy funded real time training system for power grid operators, built around the PowerSim family of simulators (3KeyMaster and WSC). To be explicit about the boundary: my part was integration, modernization, and technical leadership of the team building it, not sole authorship of the whole system.

PowerSim and WSC via 3KeyMaster → simulator state, actions, and recorded events → scoring and coaching → WPF application and database
  • Real data, not dummy data. From early 2023, my brief was to replace the placeholder data inside the scoring system with real simulator output: activity logs, simulation state, and recorded actions.
  • Legacy takeover. The codebase had gone unmaintained and was barely documented. I got the full Windows stack building and running again: the WPF application, its database, 3KeyMaster, and the custom bridge DLLs connecting them, including fixing DLL errors and rebuilding the database when the original would not come up.
  • Data pipeline. I reviewed and stabilized the simulator data retrieval path: callback handling, queued event processing in C#, state and action synchronization, and database persistence feeding the scoring system.
  • Requirements to backlog. I translated the domain experts' requirements for scoring, coaching, and communication modules into GitHub project boards, epics, issues, and programmer assignments, and ran the review loop over the team's code.
  • Compatibility and demos. I validated GOAT against newly released WSC versions before milestone demos, coordinated the external simulator teams, and helped define the follow on architecture: GOAT stays a Windows application, with a separate web based CMS for instructor scenario authoring.

Deep dive 5 · Performance

Smart Room performance, at the widget level

1000+historical points fetched to show one current value
~2xfaster widget loading after the fix
~5sfor pilot Smart Room widgets to load

The Smart Room dashboard felt slow, and the cause was a data shape problem, not rendering. Each widget only needed the latest value for its sensor, but widgets were reusing the plot's historical data fetch, pulling 1000+ points to display a single current number.

I wrote a dedicated latest value fetch for widgets, then fixed a second bug underneath it: the API was returning the first point in the requested time range instead of the newest one, so I rewrote the request parameters and added timestamp validity checks. Finally I changed widget initialization from sequential to parallel, with each widget updating as soon as its own status was ready. Widget load time fell by roughly half, and pilot Smart Room widgets loaded in about five seconds.

Case study · Personal project

MiniServe: learning LLM serving from the scheduler outward

A small LLM inference runtime I am building by hand. Most of it is a deterministic simulator where scheduling behavior can be reproduced exactly; next to it sits a real model correctness harness that runs actual prefill and decode against SmolLM2. This page keeps the two strictly separated, and labels every number as simulation or measured.

Project

MiniServe, personal project, active build

Code

github.com/jingwenzz/miniserve

Language

Python, with PyTorch for the real model harness

Status

Scheduler and simulator complete with 95 passing tests; real model prefill and decode verified standalone; batched decode is the next step

Real model used

HuggingFaceTB/SmolLM2-135M

Why build this

I wanted to understand modern inference servers from the inside: how requests are admitted, how a scheduler decides what runs in each step, why prefill and decode have different costs, and where the time to first token actually comes from. Calling a serving framework would not teach me that, so I am building the scheduling core myself and only then connecting it to a real model.

The project deliberately separates two things that are easy to blur: a simulator, which is fast and deterministic and therefore good for studying scheduling policy, and real model execution, which is where correctness has to be proven against a reference. Conflating them produces impressive and meaningless numbers, so MiniServe keeps them in separate lanes.

Read this before the numbers: Lane B is a correctness bridge. It proves I can run and verify real prefill and decode, but it is not yet integrated as the engine backend. The scheduler results below come from Lane A simulation only, and nothing on this page presents them as GPU measurements.

Scheduler design

  • Continuous batching with two limits. Each scheduling step admits and advances requests under both a batch size limit and a per step token budget, with decode work prioritized so in flight generations keep moving. There is a distinction the design keeps explicit: the per step token budget is a limit on logical work per round, and resident KV cache capacity is a separate limit; one variable cannot stand in for both.
  • Admission validation. A request whose prompt can never fit inside a single step's budget would wait forever under naive FCFS, so admission rejects oversized prompts before they enter the queue. Duplicate active request IDs are also rejected at the door.
  • Cancellation. Requests can be cancelled while waiting or while running. A cancelled request produces no further tokens, its slot and cache bookkeeping are cleaned up, and other requests are unaffected. Cancelling twice, or cancelling a finished request, is a safe no op.
  • A fair baseline. A serial scheduler that runs one request at a time shares the same engine, request types, executor, and stopping rules, so switching between serial and continuous isolates the scheduling policy as the only difference.
  • Executor boundary. The engine talks to an executor through a small protocol (prefill, decode, release), which is what will let the real model backend replace the simulated one without rewriting the scheduler.

Measurement discipline

Serving numbers are easy to produce and hard to trust, so the measurement rules were fixed before the experiments:

  • Frozen definitions. TTFT is the time from engine receipt to the first output token being available, not to prefill finishing. End to end latency runs from receipt to the completion event. TPOT is (last token time minus first token time) divided by (N minus 1) for requests with at least two tokens, and is reported as not applicable for single token requests rather than divided by zero.
  • Seeded workloads. Workload generators take a fixed seed covering prompt lengths, output limits, and arrival times, so a run can be regenerated exactly and two schedulers can be fed identical request sets.
  • Independent recomputation. Summaries are recomputed from the raw per request timelines by a separate step, and are only trusted when the recomputation matches.
  • Honest labels. Every result is labeled simulation or measured. The simulator's logical clock is never reported as model throughput.

Continuous batching finished the same workload in a third of the scheduler steps and got first tokens out sooner on average, yet each individual request took longer to complete, and the total logical time did not fall at all.

That last part is the cost model talking: the simulator charges prefill and decode work serially, so batching rearranges when work happens without making the total cheaper. The honest reading of this result is that batching trades individual completion time for system level responsiveness, and that a real throughput claim has to wait for the real executor, where one batched forward genuinely does the work of several steps at once.

The real model bridge

Lane B runs a real model: HuggingFaceTB/SmolLM2-135M, 30 layers, 3 KV heads, vocabulary 49,152. Two pieces are verified so far.

Prefill, isolated. A standalone run tokenizes a short prompt and executes prefill on its own, recording the shapes that everything else depends on:

input_ids [1, 5] · logits [1, 5, 49152] · per layer K [1, 3, 5, 64] · per layer V [1, 3, 5, 64]

Greedy decode, hand written. A manual decode loop then feeds one token at a time against the cache: 16 forwards in total (1 prefill plus 15 decode steps), every decode input shaped [1, 1], with the cache growing from length 5 to length 20 exactly one position per step. All 16 generated tokens matched the reference output exactly. Doing this by hand is what made the prefill and decode split concrete: prefill processes the whole prompt in parallel and fills the cache, decode rolls forward one token at a time on top of it, which is precisely why serving systems report TTFT and TPOT as separate metrics.

Related work: vLLM benchmarking

Kept separate on purpose. Alongside MiniServe, I have done hands on vLLM benchmarking on an A100. That work grounds the project in real serving behavior, and it is where my TTFT, TPOT, and KV cache measurement habits come from. It is a separate activity from MiniServe: no vLLM number is presented anywhere as output of the MiniServe simulator, and the serial baseline above exists precisely because outperforming a toy baseline would prove nothing about mature serving systems.

Next steps: multi prompt correctness checks for the real model harness, then batched decode, connecting Lane B to the scheduler as a real executor.
