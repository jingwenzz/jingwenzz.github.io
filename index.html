Case study · Personal project

MiniServe: learning LLM serving from the scheduler outward

A small LLM inference runtime I am building by hand. Most of it is a deterministic simulator where scheduling behavior can be reproduced exactly; next to it sits a real model correctness harness that runs actual prefill and decode against SmolLM2. This page keeps the two strictly separated, and labels every number as simulation or measured.

Project

MiniServe, personal project, active build

Code

github.com/jingwenzz/miniserve

Language

Python, with PyTorch for the real model harness

Status

Scheduler and simulator complete with 95 passing tests; real model prefill and decode verified standalone; batched decode is the next step

Real model used

HuggingFaceTB/SmolLM2-135M

Why build this

I wanted to understand modern inference servers from the inside: how requests are admitted, how a scheduler decides what runs in each step, why prefill and decode have different costs, and where the time to first token actually comes from. Calling a serving framework would not teach me that, so I am building the scheduling core myself and only then connecting it to a real model.

The project deliberately separates two things that are easy to blur: a simulator, which is fast and deterministic and therefore good for studying scheduling policy, and real model execution, which is where correctness has to be proven against a reference. Conflating them produces impressive and meaningless numbers, so MiniServe keeps them in separate lanes.

Read this before the numbers: Lane B is a correctness bridge. It proves I can run and verify real prefill and decode, but it is not yet integrated as the engine backend. The scheduler results below come from Lane A simulation only, and nothing on this page presents them as GPU measurements.

Scheduler design

  • Continuous batching with two limits. Each scheduling step admits and advances requests under both a batch size limit and a per step token budget, with decode work prioritized so in flight generations keep moving. There is a distinction the design keeps explicit: the per step token budget is a limit on logical work per round, and resident KV cache capacity is a separate limit; one variable cannot stand in for both.
  • Admission validation. A request whose prompt can never fit inside a single step's budget would wait forever under naive FCFS, so admission rejects oversized prompts before they enter the queue. Duplicate active request IDs are also rejected at the door.
  • Cancellation. Requests can be cancelled while waiting or while running. A cancelled request produces no further tokens, its slot and cache bookkeeping are cleaned up, and other requests are unaffected. Cancelling twice, or cancelling a finished request, is a safe no op.
  • A fair baseline. A serial scheduler that runs one request at a time shares the same engine, request types, executor, and stopping rules, so switching between serial and continuous isolates the scheduling policy as the only difference.
  • Executor boundary. The engine talks to an executor through a small protocol (prefill, decode, release), which is what will let the real model backend replace the simulated one without rewriting the scheduler.

Measurement discipline

Serving numbers are easy to produce and hard to trust, so the measurement rules were fixed before the experiments:

  • Frozen definitions. TTFT is the time from engine receipt to the first output token being available, not to prefill finishing. End to end latency runs from receipt to the completion event. TPOT is (last token time minus first token time) divided by (N minus 1) for requests with at least two tokens, and is reported as not applicable for single token requests rather than divided by zero.
  • Seeded workloads. Workload generators take a fixed seed covering prompt lengths, output limits, and arrival times, so a run can be regenerated exactly and two schedulers can be fed identical request sets.
  • Independent recomputation. Summaries are recomputed from the raw per request timelines by a separate step, and are only trusted when the recomputation matches.
  • Honest labels. Every result is labeled simulation or measured. The simulator's logical clock is never reported as model throughput.

Continuous batching finished the same workload in a third of the scheduler steps and got first tokens out sooner on average, yet each individual request took longer to complete, and the total logical time did not fall at all.

That last part is the cost model talking: the simulator charges prefill and decode work serially, so batching rearranges when work happens without making the total cheaper. The honest reading of this result is that batching trades individual completion time for system level responsiveness, and that a real throughput claim has to wait for the real executor, where one batched forward genuinely does the work of several steps at once.

The real model bridge

Lane B runs a real model: HuggingFaceTB/SmolLM2-135M, 30 layers, 3 KV heads, vocabulary 49,152. Two pieces are verified so far.

Prefill, isolated. A standalone run tokenizes a short prompt and executes prefill on its own, recording the shapes that everything else depends on:

input_ids [1, 5] · logits [1, 5, 49152] · per layer K [1, 3, 5, 64] · per layer V [1, 3, 5, 64]

Greedy decode, hand written. A manual decode loop then feeds one token at a time against the cache: 16 forwards in total (1 prefill plus 15 decode steps), every decode input shaped [1, 1], with the cache growing from length 5 to length 20 exactly one position per step. All 16 generated tokens matched the reference output exactly. Doing this by hand is what made the prefill and decode split concrete: prefill processes the whole prompt in parallel and fills the cache, decode rolls forward one token at a time on top of it, which is precisely why serving systems report TTFT and TPOT as separate metrics.

Related work: vLLM benchmarking

Kept separate on purpose. Alongside MiniServe, I have done hands on vLLM benchmarking on an A100. That work grounds the project in real serving behavior, and it is where my TTFT, TPOT, and KV cache measurement habits come from. It is a separate activity from MiniServe: no vLLM number is presented anywhere as output of the MiniServe simulator, and the serial baseline above exists precisely because outperforming a toy baseline would prove nothing about mature serving systems.

Next steps: multi prompt correctness checks for the real model harness, then batched decode, connecting Lane B to the scheduler as a real executor.
